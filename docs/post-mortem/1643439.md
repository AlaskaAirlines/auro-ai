# AB#1643439

## Executive Summary

The team writes a post-mortem after most significant pieces of work — sixty-six of them so far. Until now nothing read them back. The same lessons kept resurfacing in new work because there was no way for them to reach an engineer at the moment the code was being written.

This change builds the machinery that closes that loop: a new **coding standards** advisor that the AI assistant reaches for on its own whenever code is being written or reviewed, without anyone having to summon it. It is organised into ten subject areas — accessibility, forms, keyboard interaction, component lifecycle, styling, public API, build and release, testing, cross-browser support, and tooling — and it only opens the areas relevant to the task in front of it.

The work landed as **two pull requests**, and the split is the point. The first builds the machinery and ships the ten subject areas **empty**; the second fills them with fourteen rules. That separates the question *"does the advisor appear at the right moment and pick the right subjects?"* from the question *"are the rules any good?"* The first is the riskier unknown and can be tested without a single rule written, and the rules get a genuine review instead of being skimmed past scaffolding.

Also included is an automated checker that enforces the shape of a rule — most importantly that **no rule can ship without citing the ticket or pull request it was learned from**. It runs on every pull request and again on the publish path. This repository had no test suite of any kind before this work, and the checker is the only automated safety net the new system has — so the first pull request also adds a small regression suite for the checker itself, after repeated review passes found ways to feed it bad input that it accepted silently.

## The Problem

Sixty-six post-mortems had been written and nothing consumed them. A lesson learned the hard way in one component would be re-learned the hard way in another, because the only way to benefit from it was for the right person to remember the right document at the right moment.

The team already had eight AI helpers in this repository, but every one of them has to be called by name. An engineer who does not already know a standard exists will not think to ask for it — which is exactly the case where the standard would have helped most. Anything that only works when you remember to invoke it cannot fix a problem defined by not remembering.

Two further constraints shaped the approach. Standards that announce themselves on every task become noise and get ignored, so silence when nothing applies had to be designed in rather than bolted on. And a rule with no traceable source is indistinguishable from an opinion, so every rule had to be tied back to the ticket that taught it.

## Root Cause

This is net-new capability rather than a defect, so "root cause" here means the structural facts that dictated the design:

- **Nothing consumed the corpus.** `docs/post-mortem/` in this repo and in `auro-formkit` accumulated write-ups with no reader. There was no rule store, no schema, and no delivery mechanism.
- **Every existing skill sets `disable-model-invocation: true`.** All eight of them. That single key is the difference between a skill the model can reach for on its own and one that must be summoned by name. Making the standards self-triggering is therefore an *omission*, not a new mechanism (Phase 1 TRD, D4).
- **Both Copilot builders enumerate every directory under `plugins/auro/skills`** with no exclusion mechanism — the `readdir` filter in `main()` in each of `scripts/build-copilot-prompts.mjs` and `scripts/build-copilot-agents.mjs`, the same two lines in both. Creating the skill directory would make them emit `coding-standards.prompt.md` and `.agent.md`, which the two existing regenerate-and-diff gates in `check-copilot-prompts.yml` would then fail on. This is why the exclusion had to land *before* the skill directory existed, not after.
- **`auro-ai` had no automated test suite** — no unit-test runner, no Playwright, no visual regression. Regressions were caught only by the two CI drift gates and by hand, which is what makes a dependency-free schema linter worth building here rather than assuming review will catch schema drift. The same constraint shaped the linter's own tests: they are a plain Node script with no runner and no devDependency, because adding a test framework to this repo was not in scope for a scaffolding story.

## The Fix

### First pull request — the machinery

Eight commits of substantive work, landing in dependency order and numbered below. Every one carries its honest type; **merging cuts no release because this branch does not target `main`** — see *Release sequencing* below. Later `docs`-only commits correcting this post-mortem are not numbered among them, so `git log` will show a few more than eight.

**1 — `chore(copilot)`: exclude `coding-standards` from both builders.** Adds a named `EXCLUDED_SKILLS` Set beside the existing `ROOT`/`SKILLS_DIR`/`OUT_DIR` constants in both `build-copilot-prompts.mjs` and `build-copilot-agents.mjs`, and filters it out of the directory enumeration identically in each. Committed alone, before the skill directory existed, so the exclusion is provably independent of it.

**2 — `feat(coding-standards)`: the skill and its ten reference files.** `plugins/auro/skills/coding-standards/SKILL.md` (well under the 200-line cap) declares `allowed-tools: Read, Glob, Grep` and — critically — **omits** `disable-model-invocation`. Its body is ordered: a silent early exit for non-code tasks, six always-on directives, then a ten-row routing table. Rule text lives in `references/*.md`, named for the lowercased ID segment so `CS-A11Y-003` maps to `a11y.md` with no lookup table (D1). All ten files ship with their category heading and numbering rules and no rules.

**3 — `chore(scripts)`: `validate-standards.mjs`.** A dependency-free, read-only schema linter. It fails on a malformed or duplicate rule ID, an ID whose category segment disagrees with the file it lives in, a missing body, a missing or non-resolving source, a `Learned ×N` that disagrees with the distinct source count, a title over 80 characters, a file over 25 active rules, and a `SKILL.md` over 200 lines. It also fails if `SKILL.md` ever sets `disable-model-invocation`. It accumulates every error rather than stopping at the first, and prints a non-failing staleness report.

**4 — `chore(ci)`: wire it in.** Adds a `Validate coding standards` step to `check-copilot-prompts.yml`, positioned **first**, ahead of both regenerate-and-diff gates.

**5 — `docs`: this post-mortem.**

Two early corrections were squashed into the work they correct — a tidiness choice made before the branch settled on keeping later fixes separate, for the reasons set out under *Release sequencing*:

- **Into commit 2** — the first wording of always-on directive 5 was not emphatic enough to stop the model narrating an empty category. See *Iterations That Didn't Work*.
- **Into commit 3** — two parsing gaps. `parseRules` only reassigned `section` on a `## Rules` or `## Retired` heading, so any other `##` left the previous value in place — a `###` under a later prose heading was still validated as a rule and failed with a misleading "malformed rule heading", defeating the guard that exists to catch exactly that. And `TOMBSTONE_RE` captured its merge target then discarded it, so `merged into CS-A11Y-999` passed even when that ID did not exist, and the tombstone was exempted from every other field check in the same breath. Targets are now collected during parsing and resolved by a new `resolveTombstones()` once every file has been read — a merge may point at a rule in any category — with chains followed so `A → B → C` still lands on a live rule, and self-references and cycles reported.

**Three further commits landed after review, correcting the machinery rather than the rules — eight in total.** Each closed a fail-open that the previous one had partly reopened, and the sequence is the most useful thing in this document:

**6 — `fix(coding-standards)`: stop a fenced heading disarming the rule validator.** A fenced `## Retired` inside a rule body flipped the parser's section state and exempted every later rule from the field checks, so the linter printed `OK` while accepting a rule citing no source.

**7 — `fix(coding-standards)`: close the unterminated-fence fail-open and harden provenance.** Fixing commit 6 introduced a second fail-open of the same shape — an *unterminated* fence swallowed the rest of the file, so later rules were never parsed at all. The same commit added the 7-digit work-item rule and the `<repo>#<number>` source form, and carried two pieces of scope the ticket does not name: the linter's own regression suite and a second CI gate on the publish path.

**8 — `fix(coding-standards)`: stop HTML comments and a lowercase `ab#` disarming the validator.** Code review of the branch found two more, both the same shape again. `ADO_SOURCE_RE` matched only `AB#`, so `ab#1511` fell through to the repository pattern, was captured as a repo named `ab`, and skipped the 7-digit check commit 7 had just added — one shift-key slip reopening the defect that commit closed. And `parseRules` honoured `<!--` only when deciding what to accumulate as body, so a commented-out schema template satisfied the `Sources` check it was only illustrating, and a commented-out `## Retired` flipped section state for the rest of the file. Comment state is now tracked alongside fence state, an unterminated `<!--` is an error like an unterminated fence, and the reachability scan strips both.

Seven fail-opens have now been found in this linter, every one by review and none by CI. That is what the regression suite exists to change; see *Learnings*.

### The linter's own test suite

`scripts/validate-standards.test.mjs` (`npm run test:standards`) is a dependency-free Node script — no runner, no devDependency, no config, matching the constraint that produced the linter itself. Each case writes a throwaway fixture corpus to a temp directory, runs the linter against it, and asserts on exit code and stderr; the real `SKILL.md` is copied in rather than stubbed, so a routing-table change cannot silently invalidate the fixtures. It pins **nineteen cases**, one per known fail-open plus the passing cases that prove the guards did not overshoot.

### The publish-path gate

`release.yml` runs both scripts before `npm ci`. The pull-request gate is not sufficient on its own: force-pushes, ruleset bypasses and direct-to-`main` flows skip it entirely — and the release bot is itself a documented bypass of the `main` ruleset — so a corpus that never passed CI could otherwise be published. Both scripts are dependency-free, which is why they can run ahead of `npm ci`.

### Second pull request — the pilot rule set

Four commits of substantive work, numbered below, filling the ten files the first pull request shipped empty. As with the first pull request, later `docs`-only commits correcting this post-mortem are not numbered among them, so `git log` will show more than four.

**1 — `feat(coding-standards)`: fourteen pilot rules across six categories.** Distilled from six post-mortems, seeding `CS-A11Y`, `CS-FORM`, `CS-LIFE`, `CS-BUILD`, `CS-TEST` and `CS-TOOL`. `1636704` and `1344690` taught the same lesson and are authored as **one** rule citing both, exercising multi-source dedupe on day one. The four unseeded categories keep their scoped placeholders. Measured against the corpus the ratio was 49 raw lessons to 14 rules — roughly 29% survived the anti-platitude bar, which is the figure Phase 3 sizes its backfill against.

**2 — `docs(coding-standards)`: stamp `Since` and document the field syntax.** All fourteen carry `Since: 2026-09-16`, which turned the staleness report's previously inert `since=unknown` column into real data. `SKILL.md` gained the literal `- **Field:** value` grammar the linter requires, the retirement and merge-tombstone forms, and the numeric caps — all enforced before this, none of them discoverable.

**3 — `fix(coding-standards)`: cite the formkit pull requests as repo references.** Five rules cited `AB#1532` or `AB#1511`. Neither work item exists; both are `auro-formkit` **pull-request** numbers, because those lessons came from AI code review on a PR rather than from a ticket, and the `AB#` prefix had been applied by mechanical filename conversion. The citations passed every syntactic check and resolved to nothing — exactly the failure the `Sources` field exists to prevent. They now read `auro-formkit#1532` and `auro-formkit#1511`, a provenance form the schema gained for the purpose, and a short `AB#` is now rejected outright so the class cannot recur silently.

**4 — `docs(coding-standards)`: reword `CS-TOOL-002` and write up this post-mortem.** The rule said to prefix a commit by whether the file sits under `.claude/`. That is the right answer to the wrong question, and wrong in this repository specifically: here the skills *are* the published artifact, so an agent applying the rule literally would type a release-worthy commit as `chore`. It now leads with the test — does the change reach a consumer? — and keeps `.claude/` as the common case rather than the definition. This post-mortem, covering both pull requests, lands in the same commit.

## Why This Works

**The trigger is an omission, not a mechanism.** Making the skill model-invocable required deleting a line rather than adding a system. The risk is that a copy-paste from any of the eight existing skills silently re-adds `disable-model-invocation` and un-triggers the whole thing, with no visible symptom — which is precisely why the linter fails on that key rather than trusting review to notice.

**Silence is designed in, not incidental.** A false trigger costs one file read and the engineer never sees it, because the early exit is both first and silent. Always-on directive 5 goes further and forbids reporting that a category was empty. Announcing a no-op would put a line of noise on every task forever, and the announcement is exactly what makes a false positive visible when it should be invisible.

**The routing table is a set of conditions, not a classifier.** It instructs the model to evaluate every row independently and states that matching exactly one row is a signal of under-matching. This is the deliberate rejection of the obvious alternative: a validation change needs forms *and* accessibility rules together, and the worked example makes the point that the third, non-obvious match is usually the valuable one.

**Zero rules is a valid passing state, by construction.** There is deliberately no minimum-count check — a linter that demanded one rule would fail its own first commit. This is what makes the two-PR split (D7) possible.

**The linter's position in CI is load-bearing.** The two drift gates that follow it assert a clean working tree, so anything running before them that writes would make them report drift they did not cause. Running the read-only linter first makes that contract structural rather than a comment nobody checks. It also runs first because it is the only step that fails on its own exit code rather than on a diff: a red build with no diff output is then unmistakably a schema error. And it is the cheapest gate — a missing source fails in milliseconds with no reason to regenerate sixteen files first.

**The workflow and job names were left alone** despite the step being about neither Copilot nor drift. They are what branch protection matches on, and renaming would silently drop the required check.

**The linter's parser fixes were verified against a fixture per case** rather than by inspection — the corrections squashed into commit 3, above: an unresolvable merge target, a two-tombstone loop, a valid chain ending at a live rule, and a `###` under an unrelated `##`. The first two now fail with accurate messages, the third passes, and the fourth is reported as sitting outside `Rules`/`Retired` — which is what it is — instead of as a malformed heading. The reference file used as the fixture was restored byte-for-byte and the committed corpus still passes.

## Outcome

The delivery mechanism exists and is wired into the pull-request pipeline. Concretely:

- The AI assistant now has a standards advisor it reaches for on its own during code work, covering ten subject areas, that stays silent when it has nothing to say.
- Every pull request is now checked against the rule schema automatically. The rule that matters most — **no rule ships without citing the ticket that taught it** — is enforced by a machine rather than by whoever reviews the PR.
- The team's other eight AI helpers and the Copilot files generated from them are provably untouched.
- Fourteen rules ship across six of the ten categories, each citing the post-mortem or pull request that taught it. The four unseeded categories ship as scoped placeholders, ready for the Phase 3 backfill.
- **The advisor does not currently fire on its own.** Everything above describes machinery that works; S5 found that the model never reaches for it, so none of it is reaching code yet. See *The trigger does not fire*.

### Release sequencing

**Merging this cuts no release, and neither does the pilot-rule pull request.** Both merge into `phase-1a-integration` rather than `main`, and `release.yml` fires only on a push to `main`. All of Phase 1 releases as one version, when the Phase 1b gate passes and that branch merges.

The first plan typed the skill commit `feat` and merged straight to `main`, which would have published a skill with no rules in it. The Phase 1 TRD accepted that deliberately, reasoning that the riskiest unknown is the trigger, that it is testable without rules, and that the plugin's three users are the Phase 1b testers anyway. Team review reversed it: **there is no feature to use until the rules exist**, so nothing should ship claiming otherwise.

The second plan retyped every commit here to `chore`/`docs` to suppress the release. That reached the right outcome by the wrong mechanism, and it was reversed the next day. Suppression is a property of the branch, not of the commit messages — so retyping was falsifying the history to buy something the branch gives away. Honest types are restored, and the eventual release notes describe what actually landed.

An earlier plan squashed every `fix` into the work it corrects. **The reason recorded at the time was wrong and is withdrawn here:** it claimed that a fix to code which has never shipped is not a fix anyone can consume. That is not how this team works — unshipped work gets fixed routinely, and a fix is no less a fix for landing before a release.

The actual motive was narrower and is now moot. Under the retyping plan each `fix` would have cut its own patch release, publishing the same zero-rule skill under a smaller version number; on a branch that releases nothing, that cannot happen. Two early corrections had already been squashed by then and were left that way; commits 6, 7 and 8 **remain separate on the branch**, and the review trail they preserve turned out to be worth more than the tidier history — each documents a fail-open that the next one partly reopened, which is a sequence worth being able to read.

**The consequence for testing** is that no release exists at any point during Phase 1b, so every dogfooding scenario runs from a local checkout rather than the marketplace — not just S5, as an intermediate version of the plan had it. That makes one assumption load-bearing for the whole gate: a locally-installed plugin must auto-fire exactly as a marketplace-installed one does. It is checked first, and it is the single finding that would reverse this sequencing.

### The trigger does not fire

S5 was run on 2026-09-18 with the plugin installed from a local checkout of the PR-1 branch, against `auro-formkit`. **The skill never fired — in any arm, including the S1-shaped control**, and all four arms reached a real edit to component source or a test file. Zero `Skill` invocations, zero reference files opened. Full evidence and caveats are in [trigger log §5.2](https://github.com/AlaskaAirlines/auro-ai/discussions/43).

Three things follow, and they matter more than anything else in this document:

- **The install is not the blocker.** The skill was loaded and advertised to the model under its full `description` in every arm. The assumption the trigger log called load-bearing for the whole Phase 1b gate — that a locally-installed plugin behaves like a marketplace one — holds. Nothing here argues for reversing the release sequencing.
- **This is an S1 failure, not an S5 one.** S5 exists to test whether a *ticket-shaped* prompt fails where a *code-shaped* prompt succeeds. The control was code-shaped — it named a component, described a symptom, and led straight to writing a test — and it failed too. So the ticket-driven case is not the binding constraint, and S5 cannot be scored against its own reading table, every row of which presumes S1 passes.
- **The planned mitigation is probably the wrong one.** The trigger log ranks broadening the `description` as the cheap first attempt, premised on ticket vocabulary being the gap. The control rules that out. A hook on `Edit`/`Write` — which fires on the action rather than on a match — is the only listed option this evidence supports, and it is currently scheduled for Phase 4 at the earliest. Moving it is a change to the parent TRD, not a decision for these pull requests.

**What this does not settle.** Four arms, one repository, one model, one day. The result is unambiguous within that scope, but the *cause* is undiagnosed — whether the `description` is too narrow, whether it is losing to other loaded skills, or whether model-invocable matching behaves differently than the TRD assumes. Diagnosing that should precede any `description` rewrite, or the rewrite is a guess.

**It blocks neither pull request.** Nothing publishes until `phase-1a-integration` reaches `main`, so a trigger fix lands on the same branch at the same cost before or after these merge. But it should be a knowing decision rather than a later discovery, which is why it is recorded here and not left in the trigger log alone.

**It also changes what §5.1 means.** That probe found `CS-A11Y-001` did not change the generated output in a *treatment* arm — one where the model was told to read the standards. This run shows the model is not reaching them on its own at all, so the two findings are independent failures at different layers: the rules may or may not work when read, and right now they are not being read.

## Learnings

- **A standard that has to be summoned cannot fix a problem defined by not remembering it.** The single most consequential decision here was omitting one frontmatter key. Worth checking, whenever a capability is not being used, whether the barrier is the capability or the invocation.
- **Design the silent path first.** The early exit is the first thing in the file and the always-on directives forbid narrating a no-op. A skill that announces "nothing to report" on every task trains people to ignore it, and the announcement is what makes an invisible false positive visible.
- **Order commits by dependency when CI enumerates the filesystem.** The builder exclusion had to land before the skill directory existed. Landing them together would have failed both drift gates on the first pull request, and the fix would have looked like a CI problem rather than an ordering one.
- **Ship the scaffolding and the judgement calls in separate pull requests.** Rules need arguing individually against an anti-platitude bar; scaffolding is mechanical. In one diff the rules get skimmed. The split also leaves the intermediate state genuinely useful — a working skill with zero rules isolates trigger-and-routing behaviour from rule content.
- **In a repo with no test suite, a dependency-free linter is the cheapest real safety net available.** It does not need a runner, a config, or a CI service, and it converts a class of review vigilance into an exit code. The same argument then applies one level down: the linter's own tests are a plain Node script for the same reasons, and adding them cost less than the review time the defects below consumed.
- **A checker with no tests of its own is a checker nobody is checking.** Seven fail-opens were found in this linter, every one by review and none by CI, and three of them were found *after* the commit that was supposed to have closed that class. Until the regression suite existed there was no mechanism that could have caught any of them — the linter was the only safety net, and it had none itself.
- **Fixing a fail-open in one syntax invites the same fail-open in the next.** Fences were taught to the parser; HTML comments were not, so a commented-out `## Retired` reopened the exact defect the fence fix had just closed. When a guard is added for one way of writing inert text, enumerate the others in the same pass — markdown has two, and the second was found only because someone went looking.
- **Case-sensitivity is a fail-open waiting to happen when the check is a prefix match.** `AB#` was matched exactly, so `ab#1511` silently became a repository named `ab` and skipped the digit check added one commit earlier. The lowercase form is a shift-key slip, not a different kind of citation, and matching it strictly turned a typo into a bypass.
- **Put the read-only check before the gates that assert a clean tree.** Position made the read-only contract structural instead of a comment, and made a red build self-diagnosing: exit-code failure first, diff failures after.
- **The authors broke their own rule inside the branch that authored it.** `CS-TOOL-001 — Never pin a mutable identifier in a document that ships with it` was written two commits before a commit message that ended *"see post-mortem lines 60–70 … and lines 111–133."* Both ranges had rotted by the time anyone read them — they now point at unrelated sections. History is immutable so nothing was fixable, and that is the point: a rule the team violated within hours of writing it, in the medium the rule is about, is the strongest possible argument that the rule is worth having. Cite by heading, never by line number.
- **A fix can be falsified by the branch stacked on top of it.** `release.yml`'s `CS-BUILD-003` citation was removed on the machinery branch because the corpus was empty and the ID did not exist. The rule branch stacked on that one *creates* `CS-BUILD-003`, and describes exactly what that gate does. Neither change was wrong where it was made; the pair was wrong together, and nothing in a stacked-PR workflow surfaces that. When a fix's justification is "X does not exist yet," check whether the PR on top creates X.
- **A routing table is only as good as the vocabulary the reader uses.** `CS-FORM-002` is a stale-typeahead-buffer rule filed under forms, while the routing row mentioning typeahead buffers points at `intx.md`, which is empty. A task described the way its own post-mortem describes it opened the empty file and never saw the rule. Route on the *situation's* vocabulary, not the rule's filing category — and when a rule's natural vocabulary spans two categories, say so in both rows.
- **A regex capture that is never read is a check that was never written.** `TOMBSTONE_RE` captured a merge target and discarded it, which looked like validation and validated nothing. When a pattern captures a group, either use it or drop the group so the gap is visible.
- **Parser state that is only ever set, never cleared, will leak.** `section` was assigned on the two headings that mattered and left alone otherwise, so a later heading inherited stale state and defeated the guard meant to catch it. Prefer an explicit `else` that resets to a known state.
- **Verify a linter against fixtures for both outcomes.** The four fixture cases — two that must fail, two that must pass — caught that the section fix changed the *message* rather than the pass/fail outcome, which inspection alone would not have surfaced.
- **When the shell cannot write, the file tools still can.** Fixture testing in this session ran in a sandbox that denied all `bash` writes, including to `$TMPDIR`. Staging fixtures through the Write tool and restoring them the same way worked, and the tree was confirmed clean afterwards. Worth reaching for before assuming a verification step is impossible.

## Iterations That Didn't Work

- **Always-on directive 5, first wording.** The original text told the model to say nothing about an empty category. A pre-PR trigger probe fired the skill on a real code task and it worked — but the reply opened with *"Standards references are all empty stubs, so nothing to cite."* The directive was correct and simply not emphatic enough to stop the model narrating the state instead of the rules. Replaced with wording that spells out what silence means: not that a file was empty, not that there was nothing to cite, not that the standards were consulted at all. Only reachable while the corpus is empty, but the same wording governs any task where every matched category happens to hold no applicable rule.
- **Per-repo rule scoping.** An earlier pass narrowed `CS-BUILD-001` to `auro-formkit` so that Phase 1 would have a scoping exit criterion to test. The criterion turned out to be the defect. A rule scoped to the repository it was learned in is a rule silently withheld from the code that needed it — the failure mode with no signal. Per-repo scoping was removed entirely: standards apply to all Auro code in every Auro repository, `Applies to` became optional and states a *technical* precondition rather than a location, and `CS-BUILD-001` now names a Turbo precondition instead.
- **The `CS-STYL` segment spelling.** Both tickets originally wrote the styling category as `CS-STYL`. The truncation saved one character, read like a typo, and was the only segment abbreviating something already short. Renamed to `CS-STYLE` while zero rules existed — IDs are cheap to add but expensive to rename once rules cite them, and that window closes the moment the first rule is authored.
- **Two taxonomies that disagreed.** The parent TRD listed `DEPS` and `DOCS`; the tickets listed `CS-INTX` and `CS-XBRW` in those slots. The tickets won — their taxonomy was derived from the current corpus during refinement and carries per-category descriptions. Dependencies folded into `CS-BUILD` and documentation into `CS-API`, and the parent TRD was edited to match.
