# CS-A11Y — Accessibility and assistive technology

**Loaded when the task involves** ARIA state and placement, roles (explicit vs. implicit), live-region announcements, and screen-reader verification.

Rules in this file are numbered `CS-A11Y-001` upward, assigned in order, never renumbered and never reused. Maximum 25 rules; at 26 the category splits and this file's IDs stay as they are.

## Rules

### CS-A11Y-001 — Bind ARIA validity to authoritative validity, beside the role

Two shapes of this bug shipped. First, keying the binding on one *cause* of invalidity — an `error` attribute — instead of the authoritative `validity` state, so a required-and-empty control (`valueMissing`) exposed no invalid state at all; it hides because `error` and `validity` usually change together, and a `changedProperties.has('error')` branch never runs when only `validity` moves. Second, setting the attribute imperatively on the custom-element host while the `role` lives on an element inside shadow DOM, so assistive technology never associates the two. Bind declaratively in `render()` off a single `get isInvalid()` predicate, on the element that carries the role.

- **Sources:** AB#1636704, AB#1344690
- **Learned:** ×2
- **Since:** 2026-09-16

### CS-A11Y-002 — Audit sibling components for the same shape when fixing an ARIA bug

The same authoring mistake repeats across components built from the same template. `auro-checkbox-group` carried the `auro-radio-group` defect plus a worse variant, and it was found by deliberately checking for the shape rather than waiting for a second report. When two siblings do get the same fix, copy the *shape*, not the expression — the first pass shipped a different "is this invalid" predicate in each component plus a third inlined in each `render()`.

- **Sources:** AB#1636704, AB#1344690
- **Learned:** ×2
- **Since:** 2026-09-16

### CS-A11Y-003 — A role need not be explicit to be correct — check the implicit one

A native `<fieldset>` is already exposed as a group, so an added `role="group"` is redundant where `auro-radio-group` genuinely needs its `role="radiogroup"` override. Check the element's implicit role before adding one. Then check *separately* that the role supports the attribute you are about to bind — "X is the right role" and "X supports this attribute" are different claims, and only the first follows from picking the role. ARIA 1.2 deprecates global `aria-invalid` in favour of a supported-role list that includes `radiogroup` and `checkbox` but not `group`. **A role outside that list is not automatically a reason to drop the attribute:** verify with axe rather than assuming, and weigh the deprecation against what dropping it costs. On `auro-checkbox-group` the attribute is not prohibited for `group`, axe reports it clean, and removing it would discard the group-level invalid signal — so it was kept deliberately and pinned with a permanent axe assertion, which fails in CI rather than in a consumer's audit if tooling later honours the deprecation.

- **Sources:** AB#1636704
- **Since:** 2026-09-16
