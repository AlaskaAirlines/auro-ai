# AB#1643440

## Executive Summary

Phase 1a built an AI advisor that is supposed to notice on its own when someone is writing component code and quietly supply the team's own coding standards. Phase 1b — [AB#1643440](https://itsals.visualstudio.com/E_Retain_Content/_workitems/edit/1643440) — was the test of whether it actually does that. It is the only question in the effort that could not be settled on paper, and the answer decides whether the remaining phases go ahead.

**The test was run in full on 2026-09-24, and the gate did not pass.**

The advisor works, but only when the person asking already happens to use its vocabulary. Ask *"add `aria-invalid` so screen readers pick up the invalid state"* and it appears immediately, opens exactly the right topics, and writes visibly better code. Describe the same class of problem the way someone would who has never heard of the standards — *"the label stops updating after the element is moved"* — and it never appears at all. Reference a ticket number and it never appears either.

Across eleven attempts on three different dates, it has fired on **one** phrasing style and no other. That is backwards from what the effort needs: the engineer who already knows the standard exists is the one who least needs reminding.

The work also found that a result recorded in the project's own trigger log was never actually measured, and that the method everyone had been using to check these results was broken in two separate ways. Both are corrected. None of this is a reason to abandon the effort — the cause is now identified precisely, the likely fix is cheap, and the test harness is automated so re-running costs minutes instead of a day.

## The Problem

Every AI helper the team has today has to be called by name. The bet behind this effort is that a helper nobody has to summon will actually get used, and that sixty-odd post-mortems worth of hard-won lessons can reach an engineer at the moment they would otherwise repeat one.

Phase 1a delivered the advisor. Nothing had yet confirmed it does the one thing the whole plan depends on: show up uninvited, pick the right handful of topics rather than one or all ten, stay away from work that has nothing to do with code, and actually change what gets written.

Two earlier attempts to answer this had produced contradictory results and neither was trusted. One attempt was voided because the practice ticket it used had already been finished. The other appeared to succeed. Until this story ran, nobody knew which to believe.

## Root Cause

The skill's `description` field is the **entire** trigger surface (parent TRD §3.6, Phase 1 TRD §5.1). `auro-formkit` commits no `.claude` configuration, so there is nothing repo-side to help. Matching happens lexically, against the user's turn, and every trigger word in the description is code-shaped — *"writing, modifying, or reviewing code"*, *"component source, styles, tests, build/release config"*.

That works when the request shares vocabulary with the description and fails when it does not. The failure is silent: no warning, no partial load, the session simply proceeds without the rules and writes the code anyway.

The contrast pair is exact — same repo, same install, same day, minutes apart:

| Prompt | Words shared with the description | Result |
|---|---|---|
| *"`auro-select` doesn't expose its invalid state to screen readers. When validation fails, add `aria-invalid`…"* | screen readers, validation, `aria-invalid`, component name | fired at tool-use **#9**, first edit **#20** |
| *"the label on `auro-radio-group` stops updating after the element is moved in the DOM"* | component name only | **never fired**, twice |

The second session went on to edit `components/radio/src/auro-radio-group.js` directly with no rule in context. The ticket-shaped prompts behave the same way: `Implement AB#1533044` and a bare ADO URL both produced sessions that never loaded the skill, and the second of those read half of `auro-menu.js`, traced a fix to a specific commit, and wrote a gap analysis — a session that did substantial code work with the advisor sitting unused on the menu the whole time.

**Secondary root cause — the measurement was broken.** Both Phase 1 TRD §9 and the S5 re-run runbook specify shell one-liners for scoring, and both fail silently *in the same direction as a negative finding*:

- `grep -c '"skill":"coding-standards"'` cannot match. The transcript record is plugin-namespaced as `auro:coding-standards`. This produced a confirmed false negative on 2026-09-22.
- `grep -n '"name":"Edit"'` matches the **tool schemas carried in the system prompt**, not tool calls. Every transcript reports a first edit in its opening records, which makes a passing arm look like a failing one.

## The Fix

**What landed in this repository** is the measurement fix, commit `7740811`:

- `scripts/score-trigger-transcript.mjs` — parses `tool_use` content blocks out of the session JSONL rather than grepping raw lines, and reports whether the skill was advertised, the ordinal it fired at, the first edit, which reference files opened, and the resulting ordering verdict. Ordinals count every tool call, including unclassified ones, so they stay citable against the transcript.
- `package.json` — `npm run score:trigger`.
- `docs/phase-1b/arms/` — the fourteen raw arm artifacts and a README that lets them stand alone.
- `docs/phase-1b/arms/s4-v2/` — the corrected `aria-invalid` probe, its fifteen arms, and a README reading the result. `s4-prompt-v2.txt` sits beside the original so the one-word difference between them is inspectable.

**The trigger fix itself is not written yet.** That is deliberate: Phase 1 TRD §6.3 sends rework back into this story, and the trigger log's §5.2 requires diagnosis before rewriting. This run performed that diagnosis and the answer is unambiguous, so the remedy can now be chosen rather than guessed.

The recommendation is **mitigation 1 — broaden the `description`** to carry symptom vocabulary (*"stops updating"*, *"doesn't work after"*), ticket vocabulary (*"implement AB#"*, ADO URLs) and component names. The trigger log had demoted this option after 2026-09-22 on the theory that user-turn matching was already working. That theory is now known to rest on a run that was never performed.

The two alternatives were considered and ranked below it:

- **A `CLAUDE.md` committed to consuming repos** would have caught every failing arm here, but moves the standard out of the plugin and into each repo — the coupling Phase 1 exists to avoid.
- **A hook on `Edit`/`Write`** guarantees the ordering criterion by construction and is immune to phrasing, but fires on every edit regardless of relevance. That trades the S1b failure for the S3 failure, and S3 currently passes cleanly.

## Why This Works

The diagnosis is trustworthy because the alternative explanations were eliminated rather than argued away:

- **Not a broken install.** The working tree was verified to serve **15** rules, and `auro:coding-standards` appears in the tool menu of every non-baseline transcript. The skill was on the menu and was not chosen.
- **Not the scoring bug.** Every arm was scored with the corrected parser. The 2026-09-18 failures were re-scored under the namespaced pattern and remain zero.
- **Not environment drift.** The 09-18 result reproduced exactly, twice, six days later.
- **Not a duplicate project-level skill.** `auro-formkit` has no `.claude/skills/` and commits no `CLAUDE.md`; both were verified before the run.

What remains is prompt vocabulary, and S1a/S1b isolate it: one variable, two outcomes, everything else held constant.

The S4 conclusion was deliberately *not* asserted on 2026-09-24, for the opposite reason. Three baseline arms ran with the plugin genuinely absent — verified by `auro:coding-standards` appearing zero times in those transcripts — and all three produced the correct binding anyway. But the §7 fixture ships a comment reading `// authoritative: "valid" | "valueMissing" | "customError"`, and *authoritative* is the exact word the rule turns on. Every arm quoted that framing back. A probe that labels the correct source of truth in the code it hands over cannot measure whether a rule is needed to find it.

**That suspicion was correct, and the probe was re-run on 2026-09-25 with the word removed and nothing else changed.** Across nine baseline arms, one reproduced the real defect — binding `aria-invalid` off `error` rather than validity, with the ARIA write inside the existing `changedProperties.has('error')` branch, so a required-and-empty group reports `aria-invalid="false"`. That is the shape that shipped in AB#1344690 and AB#1636704. All five arms with the rule in context were clean. Under the original fixture the defect never appeared in four arms; removing one word produced it.

So the rule is **not** a platitude and the recommendation to consider cutting it is withdrawn. What the re-run does *not* show is a clean control-fails / treatment-passes split: eight of nine baselines got it right unaided. Scoring a defect that surfaces in roughly one arm in nine is a judgement call for the team. Full arms and a longer reading are in `docs/phase-1b/arms/s4-v2/`.

## Outcome

The hard gate did not pass, and the remaining phases stay on hold — which is the outcome the gate exists to produce when the answer is no. What the team has instead:

- A precise, evidence-backed cause for the one behavior the whole effort depends on, where before there were two contradictory results and no explanation.
- A cheap first remedy, with two fallbacks ranked behind it and reasons for the ranking.
- An automated test harness. Re-running the discriminating scenarios now costs minutes; the three prior attempts each cost most of a day and two of them produced nothing usable.
- Four corrections to the project's own records, including one result that was recorded but never measured.

Nothing shipped to consumers and nothing could have: this story changes no published code. The advisor remains unreleased, which is the correct state for something that does not yet work reliably.

**Still blocked on the GitHub account suspension:** posting the evidence to Discussion #43, the team review that formally closes the gate, and merging `phase-1a-integration` into `main`. The evidence is written and banked locally so none of it has to be redone.

## Ticket Completeness

**1 of 5 acceptance-checklist items fully resolved.** One is partial, one is contested pending a team decision, and two are not resolved. A sixth requirement — the local/marketplace equivalence prerequisite — is buried in the criteria prose rather than the checklist, and is also not resolved.

**Resolved**

- **Routing narrows rather than loading everything.** The session opened three of ten topic areas — accessibility, forms, testing — and left seven closed, including all three the ticket names (`CS-BUILD`, `CS-TOOL`, `CS-XBRW`). Every opened area is defensible for the task. Note this clears the ticket's wording, which is stricter than the plan's: the plan treated `CS-TOOL` as exempt, and it stayed closed anyway.

**Not Resolved / Partial**

- **Partial — the trigger fires and routes to a defensible subset.** The literal criterion is met: a session asked to add validation to a form component loaded the skill unprompted and opened `CS-FORM` and `CS-A11Y` at minimum. But that holds only for a request already phrased in the skill's vocabulary. The same class of problem phrased as a symptom never fires, in two independent runs. The pending §6.1 addition exists precisely because one prompt cannot distinguish a working trigger from a narrow one, and by that addition this fails.
- **Not resolved — it does not over-fire.** *(Scenario passed; criterion cannot be closed.)* The unrelated-task session never loaded the skill, across a 150-record session that cloned repositories and walked commit history. The scenario result is clean, but it cannot be signed off independently of the gate it feeds.
- **Contested — the rule changes the output.** *(Re-run 2026-09-25; needs a team decision.)* The criterion requires the request to reproduce the `1636704` defect *without* the skill. On the original fixture it did not, but that fixture named the answer in a comment. On the corrected fixture it **does** reproduce — in one baseline arm of nine, with all five treated arms clean. Read literally the criterion is met; read as "reliably reproduces" it is not. The before-and-after outputs the ticket asks for are captured verbatim and committed either way. See **Why This Works**.
- **Not resolved — dogfooding checkpoint (hard gate).** Results are not recorded in Discussion #43 and no team review has happened. Both need GitHub. The evidence document is written and parked in `.s5-scratch/phase-1b-evidence.md`, to be posted as a TRD once access returns.
- **Not resolved — the local/marketplace equivalence prerequisite.** The acceptance criteria require confirming *before S1* that a local install auto-fires identically to a marketplace one, and call its failure the one finding that would reverse the decision to hold the release. **This was not tested.** The local install was verified to work, to load in place from the working tree, and to serve 15 rules — but equivalence was never established, because the marketplace copy serves `main`, which contains no `coding-standards` skill at all, and GitHub is unreachable. Every scenario below it therefore rests on an unverified prerequisite. This does not change the failures — a skill that never fires cannot be rescued by a better install — but it is a real gap in the passing results.

## Learnings

- **A skill's `description` is a lexical matcher, not an intent classifier.** It fires on vocabulary overlap with the user's turn. Any skill meant to trigger unprompted must carry the words users actually type — including symptom phrasing and ticket references — not only the words its authors use to describe it.
- **The people who most need an unprompted helper are the ones least able to summon it.** Firing only on domain vocabulary inverts the value: it helps whoever already knows, and stays silent for whoever does not.
- **A recorded result is not a run result.** The trigger log's 🟢 entry for ticket-driven invocation was an assumption — the ticket-shaped prompt was never executed, and the plain-language run that did succeed was filed under its heading. It was first actually run on 2026-09-24, and failed both arms. Evidence entries should distinguish *measured* from *expected*.
- **Verify the measurement before trusting a negative.** Two independent bugs in the documented scoring method both failed in the same direction as the finding. A negative result produced by an unvalidated method should be re-derived before it is acted on.
- **"Open in the tracker" does not mean "unimplemented in the repo."** Three consecutive fixture tickets were voided this way — one closed, one assigned and in progress, and one whose fix had already landed under a different ticket (`AB#1533044`, fixed by `AB#1602086` via `_sortSelectedByDomOrder()` in `components/menu/src/auro-menu.js:949`). Fixture selection needs a repo-side check.
- **A probe that names the answer measures nothing — demonstrated, not argued.** The `aria-invalid` fixture labelled `validity` as *authoritative* in a code comment: the precise concept under test. Removing that one word, changing nothing else, turned a probe that found no defect in four arms into one that reproduces the real production defect. Probe fixtures should be read adversarially for tells before they are run, not after they produce a surprising result.
- **Sample size is part of a probe's specification.** The defect surfaces in roughly one baseline arm in nine, so a three-arm probe would have found nothing most of the time and "the rule is a platitude" would have looked well-supported. A probe for a non-deterministic behavior needs a stated n, chosen from the effect size it is trying to detect.
- **A surprising result is a reason to audit the instrument first.** Both of this phase's biggest errors — the scoring greps and the leaky fixture — produced clean, plausible, wrong answers. In both cases the finding pointed the same direction the bug did, which is precisely when it is least likely to be questioned.
- **Scripting the harness changes what is affordable.** Pinning each arm to a named session made repeat runs cheap enough to run S1b twice and the S4 baseline three times. The single-run results from earlier attempts could not have distinguished a genuine failure from non-determinism.

## Iterations That Didn't Work

- **The §3 version of the `aria-invalid` probe was abandoned before running.** It asks only for "a component binding `aria-invalid`" — the same under-specified shape that produced contradictory results on 2026-09-16 and 2026-09-22. Running it again would have bought a third ambiguous answer. The §7 specification was used instead, which needed no build work: it already supplied a realistic pre-fix fixture, a neutral prompt, and a single discriminating assertion.
- **The first S4 treatment arm had to be discarded.** It ran with the plugin installed and available, per §7's protocol — but the skill never fired on §7's neutral prompt, so the arm measured the untreated model with extra steps. A second arm that explicitly invokes the skill was added to obtain a genuinely treated sample. The non-firing is itself a data point, and it is counted as one.
- **`AB#1642340` was dropped as the S5 fixture.** It is Active and assigned, so implementing it would have collided with work in progress. Its replacement `AB#1533044` then turned out to be already fixed on `dev`, which is what surfaced the fixture-selection gap above.
- **Interactive sessions were not used.** Prior attempts were driven by hand. Every arm here ran headless via `claude -p` with a pinned session ID, for repeatability. This is a third variable that moved relative to the 09-18 and 09-22 runs and is recorded rather than hidden; the mitigation is that S1b reproduced the interactive 09-18 result exactly, twice.
