PR #1625 — menu: remove disabled prop propagation

PR #1625 by Sun Mota (@sun-mota) · tickets: AB#1566578 · Before = __BEFORE_SHA__ (merge base with dev) · After = __AFTER_SHA__ (PR head). Both columns run the real component source from those commits.

The problem

Disabling an auro-menu copied disabled onto every option. Re-enabling it copied false back, so options that were deliberately unavailable, like a sold-out fare, became selectable again.

The fix

The menu no longer writes to its options. Each interaction path (keyboard, click, hover, setting value) now checks the option's parent menus at the moment it runs, and aria-disabled still tells screen readers the options are unavailable.

1. Disable, then re-enable the menu

What to look for: "First — sold out" is authored disabled. After a disable → re-enable cycle, Before force-enables it; After leaves it disabled.

2. A disabled menu still can't be used

What to look for: with the menu disabled, clicking an option and setting value select nothing on either side.

Open questions

  • Cosmetic gap, accepted in the SCSS: when the root menu is disabled but a nested submenu isn't, a selected option inside that submenu keeps its highlight color. It still can't be used. Is that acceptable to design?
  • Not breaking, per the team's rule: while the menu is disabled, option.disabled now stays false (see economy.disabled). The menu no longer copies its state onto its options; an option's own disabled is set on the option.
